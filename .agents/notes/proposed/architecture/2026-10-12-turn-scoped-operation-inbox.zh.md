# 异步任务结果：保存、排队与派发

Status: proposed
Type: architecture
Translation: current

[English](2026-10-12-turn-scoped-operation-inbox.md)

## 摘要

一个对话把工作交给其他对话后，对方可能稍后才交回结果。结果先保存；主对话忙时不打断，正常答完且实际释放后合批处理，用户暂停后不能自动继续。用户后来发新消息时，把已有结果与新消息放进同一次模型输入，优先处理用户的新要求。本文解释确认后的设计方向、8 个结果的例子、独立模块和测试；实现及验收状态见下文。

## 当前实施范围

用户已授权完整施工：收件箱、持久 Stop、合批、Effect 内核及主流程均已接入。本文仍是待 review 的设计记录；具体实现及验证见[计划](2026-10-12-operation-inbox-effect-implementation-plan.zh.md)和[实现记录](../../implemented/architecture/2026-10-12-operation-inbox.zh.md)。反向 chat 保留原名和既有限制，不新增 note 工具或任务图。

Stop 前排队但未执行的旧用户输入只保留历史、取消执行资格；恢复时只带结果资料，用户要重新执行旧指令需重新发送。执行失败不自动合批；释放不明还会挡住新用户执行。

## 先认识四个词

假设主对话 A 请其他对话帮忙检查 8 个文件。

- **Operation（异步任务）**：A 发出去的一份工作请求；结果可能还没回来。
- **结果队列（queue）**：已经完成、但 A 尚未处理的结果。成功、失败、取消都算结果；仍在运行的任务不在这里。
- **一次运行（turn）**：Agent 收到一份输入，到本次回答或执行结束。一个用户任务可以经过多次运行。
- **派发**：把结果交给模型处理。保存结果不等于派发结果。

“自然结束”和“用户暂停”是两件事。暂停期间没有新用户消息时，结果只能保存。用户后来发消息，开启新的运行轮次，已有结果自动带入；这次运行正常结束后重新遵循自然结束的规则。用户无需知道 Operation，也没有额外按钮。

## 1. 六条不能打破的规则

1. **先保存，再决定是否运行。** 不派发也不能丢结果。
2. **忙时只排队。** 子任务结果不能打断正在处理的用户输入。
3. **暂停后禁止自动继续。** 暂停必须保存到磁盘；迟到结果、重启或刚变空闲都不能解除它。下一条由用户主动发送的消息开启新轮次，并带入已有结果。
4. **用户输入优先。** 尚未提交的自动批次让位给新用户消息。
5. **一次取全部，一次交付。** 在选定的时刻，全部可处理结果组成一条消息；不是一项结果运行一次模型。自然结束即可合批，不要求 Agent 额外登记等待。
6. **同一结果不重复执行。** 重试和重启保持同一身份。提交后不知是否收到，就保留“未知”，不能直接再发。

任务结果是参考资料，不是新的用户指令。“收到”“请确认收到”不应创建反向任务。只有用户本人从可信 UI／CLI 入口新发的消息才有恢复授权；其他 Agent 发来的 chat 即使在历史中显示为 user，也不能解除暂停。

新用户任务保持自己的身份、配置和调用深度。例如新任务深度是 0，附带一项深度 15 的旧结果，仍按深度 0 处理新委派。旧结果的深度只是来源资料。只有自动处理结果的后续运行才继续遵守原来的最大调用深度。

## 2. 最基础的行为

| 发生什么 | 系统做什么 |
| --- | --- |
| A 发出 Operation | 记录任务、发信人、所属用户任务；不要求 A 一直等 |
| 对方交回结果 | 保存结果，加入 A 的队列 |
| A 正在忙 | 只排队，不调用模型 |
| 执行失败／释放不明 | 结果只保存，等新用户消息；释放不明还会阻止继任执行 |
| A 正常结束本次运行 | 等旧执行释放资源，再按下节规则选下一份输入 |
| 用户暂停／中断 | 先关闭自动运行许可，再取消当前运行；队列保留 |
| 用户发新消息 | 允许处理这条消息，准备输入时带上当前队列 |
| 会话归档、删除或整树停止 | 结果留作记录，遵循现有的禁止执行边界 |

暂停主任务不等于撤销子任务已做过的事情。停止整棵任务树是另一个明确操作，已返回的结果仍保留。

## 3. 什么时候派发

**结果到达只保存，不获得唤醒资格。** 派发只发生在当前运行自然结束且真实释放的边界，或下一条用户输入开始时。自然结束时固定当时队列的水位；结束后才到达的结果不叫醒已经空闲的对话。重启只可恢复已经记录、尚未提交的自然结束派发意图，不能扫描队列后创建新的唤醒。恢复这项检查不需要新事件推动；即使用户不再发消息，也应完成原本已获准的派发。每次自然释放只记录一次水位，重复通知不能把后来到达的第 9 项加入旧批次。空队列也记录这个边界，但只有固定水位内有可处理结果才生成派发意图。认领时已无结果则原子结清意图，不创建自动执行；自动批次必须至少有一项结果。

真正提交输入前，按此顺序决定：

```text
会话禁止执行？       → 结果只留作记录
正在忙或尚未真实释放？ → 排队，等旧执行真实退出
有获准的新用户输入？ → 一次用户调用，有结果则一并带入，无结果走原路径
用户已暂停？         → 不自动调用；等用户
有自然结束派发意图？ → 按固定水位取结果；非空才调用，空则结清意图
以上都没有？         → 保持空闲
```

用户消息只带入结果资料，旧任务结果不能覆盖新要求。自然结束允许合批；用户暂停阻止自动合批。这两种退出原因必须由执行系统记录，不能共用一个“空闲”标志，也不能从助手文字猜测。已经归档、删除或停止整树的会话继续受现有边界约束。

### 例子 A：8 项都在 queue，A 正在忙

不发送。A 正常结束、旧执行实际释放后，一次取出这 8 项，额外运行一次，不需要登记等待。

```text
A 正在忙 → 8 项排队 → 正常结束 → 一条含 8 项的消息 → 运行一次
```

不能仅看界面显示空闲：旧请求还没结束，就不能放行下一轮。

### 例子 B：8 项排队，用户点击暂停

8 项保留，新增模型输入为零。第 9 项后来到达也只保存。重启应用仍保持暂停。

用户随后问“目前做完了什么”，把这句话与已有结果一起交给模型，由新要求决定如何处理；不先运行旧结果。用户消息开启新轮次，这次自然结束后重新遵循正常派发规则，不需要额外的继续按钮。

### 例子 C：8 项排队，用户也发了一条新消息

推荐**随用户消息一起交付**，不用先回答用户再额外启动结果处理：

```text
同一次模型输入
  用户要求：先别改代码，告诉我 8 个检查的结论。
  任务结果：1…8 的来源、状态和结果。
```

两部分保持独立结构，以用户要求为准。这样少运行一轮，也避免模型先按旧要求做事，再看到新要求。

用户消息如果在 A 忙时到达，先排队；轮到它执行时才取结果快照。快照后到达的第 9 项留在队列，不改变已准备好的输入。

### 例子 D：预计有 8 项，只完成了 3 项

默认合并当前已有的 3 项，不强制等齐 8 项。模型可以先处理这 3 项，并说明其余 5 项还未结束。业务必须等齐才能下结论时，由调用方保留这个业务条件；本次不新增等待登记工具。

### 暂停与派发同时发生怎么办

Stop、新用户消息的接受和实际请求启动必须共用一个短期准入入口。暂停或用户消息先被接受：旧自动批次不能再提交，结果保留或随新消息交付。启动先取得准入：随后暂停取消这次已发起的执行，不能撤回或重发结果。不能在“暂停已保存”与“请求启动”之间只靠一次旧检查。点击尚在等待准入时，系统不能提前确认暂停成功；落盘失败必须告知用户并禁止本进程自动派发。

运行中的旧 turn 与已经排队的新用户输入分别记录。接受新消息不能让针对仍在执行的旧 turn 的 Stop 失效。请求忽略取消时，等待者退出或 Scope 关闭都不算真实释放；未结束资源要继续有人负责恢复，确认结束后才允许下一轮。详细准入与资源契约见[实现计划第 2–3 节](2026-10-12-operation-inbox-effect-implementation-plan.zh.md)。

### 哪些结果算过期

投递已消费或未知、所属会话已删除／归档、整树停止或当前仍暂停时，结果不能自动唤醒。仅仅尚未超过 deadline 不足以判断能否派发。旧结果作为资料保留原身份、来源和时间，不重新执行旧提示；缺少可验证来源的升级积压留给下一条用户消息。

自然结束后合批、用户暂停后等待新消息，是本设计的选择，不是所有 harness 的通用行为。

## 4. 怎么测试

先用可控制的假模型测规则，再用真实 SQLite 测保存和重启；不依赖真实网络或 sleep。

| 场景 | 必须观察到 |
| --- | --- |
| 忙时收到 8 项 | 队列有 8 项，没有新模型输入 |
| 普通 turn 空队列自然结束 | 保留边界记录，不产生可派发意图，零次额外提交 |
| 8 项消费完后再次自然结束，队列为空 | 不启动下一次空批次，零次额外提交 |
| 空边界后结果迟到＋重复释放＋重开 | 只保存迟到结果，原空边界不扩大水位，零次额外提交 |
| 正常结束后已有 8 项 | 一份输入包含全部 8 项及各自来源，不要求登记等待 |
| 提交前暂停 | 没有模型输入，8 项仍可读取 |
| 暂停后第 9 项到达／重启 | 只保存，不自动运行 |
| 暂停后用户问进度 | 一份“用户消息 + 结果”；按新要求运行，新轮次正常结束后可继续合批 |
| 新用户消息与自动批次竞争 | 提交前用户优先，结果不丢、不重复 |
| 选好批次后第 9 项到达 | 原批次不变，第 9 项仍排队 |
| 自然结束边界之后第 9 项才到达 | 只保存，不唤醒空闲对话 |
| 重启时有未提交的自然结束派发意图，没有任何新事件 | 自动恢复原水位批次，再检查暂停和用户优先；不加入后到结果 |
| 释放时 8 项，第 9 项迟到，再重复通知并重开 | 仍只恢复原来 8 项，第 9 项不能叫醒对话 |
| 新用户任务深度 0，附带旧结果深度 15 | 新任务仍以深度 0 委派；自动续跑遵守原最大深度 |
| Agent chat 在暂停期间到达 | 不把它当作用户本人恢复授权 |
| 两个 Worker 同时派发 | 同一结果不能重复处理 |
| 写历史成功，模型提交未知 | 保留未知，不重发，用户可手动处理 |
| 归档、删除或整树停止后结果迟到 | 留记录，不唤醒会话 |
| 执行失败退出 | 保存结果、没有自动意图，等下一条用户消息 |
| 取消等待、并发关闭或清理失败 | 未结束工作仍有所有者和恢复句柄；确认真实释放前没有继任输入 |

检查实际输入、数据库结果和释放状态，不只数 mock 调用。用 Deferred 控制竞争、注入时钟和 fake timers 控制时间，用真实文件数据库重开验证持久状态。

## 实现附录：独立的 Effect 模块

建议叫 `OperationInbox`，只负责**有哪些结果、能否运行、交哪一批**，不依赖模型供应商、聊天界面或历史存储的内部实现。

| 部分 | 职责 |
| --- | --- |
| 纯规则 | 决定排队、用户优先、合批或禁止运行 |
| Effect 服务 | 保存、串行调度、等待、取消、恢复 |
| SQLite adapter | 原子保存暂停、任务身份、批次成员和提交状态 |
| 执行 adapter | 一次投递，报告已提交／未提交／未知，等待真实清理 |

主流程只报告开始、正常结束、用户暂停、新用户输入及失败／恢复这些事件。服务使用锁定的 Effect `4.0.2`、Service／Layer 与 Scope 管理的 fiber；测试替换存储及执行 adapter。不把旧 `continueSession` 整体 Promise 包装后称为充分 Effect 化。具体交付步骤见[实现计划](2026-10-12-operation-inbox-effect-implementation-plan.zh.md)。

每批有固定 ID、一次事务和稳定成员。正文太大时保留全部成员索引，分页读取全文，不能拆成 8 次模型运行。新模块上线必须关闭旧逐 Operation 续跑；缺少可靠任务身份的旧积压只可读取，切换须排空或确认终止旧请求，不能只相信旧 coordinator.stop() 已返回。仅支持实现相同移交协议的降级版本；具体 SHA／schema 矩阵需在实施前固定，不兼容版本在获得写权前拒绝，不能恢复旧唤醒。实施前更新现有 [Session 编排 Spec](../../../../specs/session-orchestration.zh.md)。
